# Rust 代码模块如何组织：`lib.rs`、`mod`、`use` 与最佳实践

Rust 的模块系统同时解决三个问题：

- **代码分组**：把相关类型和函数放在同一个模块中；
- **可见性控制**：决定哪些实现细节对外公开；
- **路径命名**：通过稳定、清晰的路径引用代码。

初学时最容易混淆的是 `mod`、`use` 和 `pub use`：

```text
mod      声明模块，告诉编译器模块属于当前 crate
use      把一个路径引入当前作用域，减少重复书写
pub use  引入路径并重新公开，设计对外 API
```

模块设计的核心目标不是把文件切得越多越好，而是建立清晰的职责边界和依赖方向。

## 1. 先理解 package、crate 和 module

### 1.1 Package

Package 是由一个 `Cargo.toml` 描述的 Cargo 项目。一个 package 可以包含：

- 最多一个 library crate；
- 任意多个 binary crate；
- examples、tests 和 benchmarks 等目标。

### 1.2 Crate

Crate 是 Rust 编译器一次编译的代码单元：

- `src/lib.rs` 是默认的 library crate 根；
- `src/main.rs` 是默认的 binary crate 根；
- `src/bin/*.rs` 中的每个文件通常是一个额外的 binary crate 根。

如果同一个 package 同时有 `src/lib.rs` 和 `src/main.rs`，它们是两个不同的 crate，只是属于同一个 package。

### 1.3 Module

Module 是 crate 内部的命名空间和可见性边界。模块可以嵌套，并形成模块树：

```rust
mod network {
    pub mod client {
        pub fn connect() -> &'static str {
            "connected"
        }
    }
}

assert_eq!(network::client::connect(), "connected");
```

这里 crate 根下面有 `network`，`network` 下面又有 `client`。

## 2. `lib.rs` 和 `main.rs` 分别做什么

### 2.1 `src/lib.rs`：库的根与公共 API 入口

`lib.rs` 是 library crate 的根模块，适合：

- 声明顶层模块；
- 重导出主要公共类型和函数；
- 放置 crate 级文档；
- 保持为一张简洁的公共 API 地图。

推荐让 `lib.rs` 保持精简：

```rust,ignore
//! 用户服务库。

mod config;
mod error;
pub mod user;

pub use config::Config;
pub use error::Error;
pub use user::UserService;
```

业务实现通常不应全部堆在 `lib.rs` 中。

### 2.2 `src/main.rs`：程序组装与启动入口

`main.rs` 适合完成应用组装：

- 读取命令行参数和配置；
- 创建数据库、网络客户端等基础设施；
- 调用 library crate 提供的业务 API；
- 决定顶层错误如何记录以及进程如何退出。

```rust,ignore
use user_service::{Config, UserService};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::from_env()?;
    let service = UserService::new(config);
    service.run()?;
    Ok(())
}
```

当 package 同时包含库和二进制时，`main.rs` 应通过**包的库 crate 名称**导入库代码，而不是再次写 `mod` 编译同一批文件。

如果 package 名是 `user-service`，Rust 路径中的 crate 名通常写成 `user_service`，连字符会转换为下划线。

### 2.3 为什么推荐“薄 `main.rs`，主要逻辑在库中”

这样组织通常有几个好处：

- 业务逻辑可以被集成测试直接调用；
- 多个二进制入口可以复用同一套实现；
- `main` 只负责进程级决策，职责更清晰；
- 库 API 迫使模块边界变得明确；
- 后续创建 example、benchmark 或其他前端更容易。

## 3. `mod`：声明模块

### 3.1 内联模块

模块内容可以直接写在花括号中：

```rust
mod math {
    pub fn add(left: i32, right: i32) -> i32 {
        left + right
    }
}

assert_eq!(math::add(20, 22), 42);
```

内联模块适合很短的私有实现和测试模块。业务模块较大时，通常拆到独立文件。

### 3.2 文件模块

在 `src/lib.rs` 中声明：

```rust,ignore
mod config;
```

编译器会查找以下形式之一：

```text
src/config.rs
src/config/mod.rs
```

两种形式都受支持。现代项目通常优先使用 `src/config.rs`，减少大量同名的 `mod.rs` 文件。

重要的是：`mod config;` 不是导入语句，也不是 C/C++ 的文本包含。它声明 `config` 是当前模块的子模块，并让对应文件参与 crate 的模块树。

### 3.3 子模块的文件布局

假设 `src/user.rs` 中有：

```rust,ignore
mod repository;
mod service;
```

编译器会从父模块 `user` 对应的目录寻找：

```text
src/
├── lib.rs
├── user.rs
└── user/
    ├── repository.rs
    └── service.rs
```

另一种等价布局是：

```text
src/
├── lib.rs
└── user/
    ├── mod.rs
    ├── repository.rs
    └── service.rs
```

一个模块在模块树中只应有一个定义位置。不要同时创建 `src/user.rs` 和 `src/user/mod.rs` 来定义同一个模块。

### 3.4 `mod` 通常只在父模块声明一次

如果 `lib.rs` 已经声明 `mod user;`，其他模块要使用 `user` 时应通过路径引用，不要重复声明：

```rust,ignore
// src/lib.rs
mod user;
mod order;
```

```rust,ignore
// src/order.rs
use crate::user::User;
```

重复写 `mod user;` 不是“导入 user”，而是尝试声明当前模块自己的 `user` 子模块，并会改变编译器查找文件的位置。

## 4. `use`：把路径引入作用域

### 4.1 基本用法

```rust
mod domain {
    pub struct User {
        pub name: String,
    }
}

use domain::User;

let user = User {
    name: String::from("Alice"),
};

assert_eq!(user.name, "Alice");
```

没有 `use` 也可以使用完整路径：

```rust
mod domain {
    pub struct User;
}

let _user = domain::User;
```

`use` 只是为当前作用域创建一个较短的名称，不会改变目标项的所有权，也不会绕过可见性规则。

### 4.2 推荐的导入风格

导入类型时，通常导入到类型本身：

```rust
use std::collections::HashMap;

let users: HashMap<u64, String> = HashMap::new();
assert!(users.is_empty());
```

导入函数时，保留一层模块名有时更能说明来源：

```rust
use std::fmt;

fn format_error(formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
    write!(formatter, "failed")
}
```

这不是硬性规则。目标是避免名称冲突，并让调用位置容易理解函数来自哪里。

### 4.3 分组导入

```rust
use std::{
    collections::{HashMap, HashSet},
    io::{self, Read},
};

let map: HashMap<u32, u32> = HashMap::new();
let set: HashSet<u32> = HashSet::new();
let _reader_trait: Option<&dyn Read> = None;
let _io_result: io::Result<()> = Ok(());

assert!(map.is_empty());
assert!(set.is_empty());
```

分组不要嵌套得过深；如果导入语句比展开后更难读，应拆成多行独立 `use`。

### 4.4 使用 `as` 解决名称冲突

```rust
use std::fmt::Result as FmtResult;
use std::io::Result as IoResult;

fn formatting_result() -> FmtResult {
    Ok(())
}

fn io_result() -> IoResult<()> {
    Ok(())
}

assert!(formatting_result().is_ok());
assert!(io_result().is_ok());
```

### 4.5 通配符导入要谨慎

```rust
use std::collections::*;
```

`*` 会把模块中所有公开名称引入作用域，可能导致：

- 来源不清晰；
- 新增上游 API 后产生命名冲突；
- 代码审查时难以判断实际依赖。

生产代码通常优先显式导入。测试模块中使用 `use super::*;` 导入被测模块的内容较为常见。

## 5. 路径：`crate`、`self` 与 `super`

### 5.1 `crate::`：从当前 crate 根开始

```rust
mod domain {
    pub struct User;
}

mod application {
    use crate::domain::User;

    pub fn create_user() -> User {
        User
    }
}

fn main() {
    let _user = application::create_user();
}
```

跨顶层模块引用时，`crate::...` 清楚而稳定，是库内部常用的绝对路径。

### 5.2 `self::`：从当前模块开始

```rust
mod service {
    pub struct UserService;

    pub fn build() -> self::UserService {
        self::UserService
    }
}

let _service = service::build();
```

许多场景可以省略 `self::`，但它在重导出和强调当前模块时很有用。

### 5.3 `super::`：从父模块开始

```rust
mod user {
    pub struct User {
        pub active: bool,
    }

    mod validation {
        use super::User;

        pub fn is_valid(user: &User) -> bool {
            user.active
        }
    }

    pub fn validate(user: &User) -> bool {
        validation::is_valid(user)
    }
}

let user = user::User { active: true };
assert!(user::validate(&user));
```

`super` 适合紧密相关的父子模块。大量 `super::super::super` 往往说明模块层级过深或依赖方向需要调整，跨较远模块时可考虑 `crate::` 路径。

### 5.4 外部 crate 路径

Rust 2018 及以后通常直接从依赖 crate 名开始：

```rust,ignore
use serde::Serialize;
```

大多数普通场景不再需要写 `extern crate serde;`。宏、FFI 或兼容旧版本等特殊情况应以具体文档为准。

## 6. `pub` 与可见性

Rust 中的项默认是私有的。私有项可以被其所在模块及后代模块访问，但父模块不能直接访问子模块的私有项。

### 6.1 `pub` 不会递归公开所有内容

```rust
mod account {
    pub struct User {
        pub name: String,
        password_hash: String,
    }

    impl User {
        pub fn new(name: String, password_hash: String) -> Self {
            Self { name, password_hash }
        }

        pub fn has_password(&self) -> bool {
            !self.password_hash.is_empty()
        }
    }
}

let user = account::User::new(
    String::from("Alice"),
    String::from("hash"),
);

assert_eq!(user.name, "Alice");
assert!(user.has_password());
// user.password_hash 是私有字段，外部无法直接访问。
```

即使结构体是 `pub`，字段仍然默认私有。这样可以保护不变量，并允许以后修改内部表示。

同样，`pub mod user` 只公开模块路径，模块内部的项仍需分别声明为 `pub`。

### 6.2 限制范围的可见性

Rust 支持比 `pub` 更精确的范围：

```text
pub             对能够到达该路径的外部代码公开
pub(crate)      只在当前 crate 内公开
pub(super)      只对父模块公开
pub(self)       只在当前模块公开，等同于默认私有
pub(in path)    只在指定的祖先模块范围内公开
```

示例：

```rust
mod service {
    pub(crate) fn initialize() -> &'static str {
        "initialized"
    }

    pub(super) fn internal_status() -> &'static str {
        "ready"
    }
}

assert_eq!(service::initialize(), "initialized");
assert_eq!(service::internal_status(), "ready");
```

最佳实践是从最小可见性开始，只在确实需要跨边界使用时扩大范围。

### 6.3 公共 API 不应泄露私有实现类型

公共函数的参数和返回类型也是 API 的一部分。不要让公开接口依赖调用者无法命名或不应知道的私有类型。

更稳妥的方式是：

- 返回公开的领域类型；
- 返回 trait 抽象；
- 在公共边界转换成稳定的数据结构；
- 将实现类型保持在私有模块内。

## 7. `pub use`：重导出并设计公共 API

假设类型实际定义在较深路径：

```rust
mod domain {
    pub mod user {
        pub struct User {
            pub name: String,
        }
    }
}

pub use domain::user::User;

let user = User {
    name: String::from("Alice"),
};

assert_eq!(user.name, "Alice");
```

没有重导出时，调用路径是 `domain::user::User`；重导出后，可以从当前模块直接使用 `User`。

在库的 `lib.rs` 中，`pub use` 可以建立一个稳定、易发现的门面：

```rust,ignore
mod error;
mod service;

pub use error::Error;
pub use service::UserService;
```

外部用户可以写：

```rust,ignore
use user_service::{Error, UserService};
```

内部文件以后可以重组，只要公共重导出路径不变，调用者就不需要修改。

### 7.1 不要把所有内容都重导出

`pub use module::*` 会让公共 API 快速膨胀，并使名称来源和兼容性承诺变得模糊。建议只重导出调用者真正需要的核心类型、trait 和函数。

公共 API 越小：

- 文档越容易浏览；
- 破坏性变更越少；
- 内部重构空间越大；
- 用户越容易找到推荐入口。

## 8. 一个推荐的单 crate 项目布局

下面是一个按业务功能组织的用户服务：

```text
user-service/
├── Cargo.toml
├── README.md
├── src/
│   ├── lib.rs
│   ├── main.rs
│   ├── config.rs
│   ├── error.rs
│   ├── user.rs
│   └── user/
│       ├── model.rs
│       ├── repository.rs
│       └── service.rs
├── tests/
│   └── public_api.rs
└── examples/
    └── basic.rs
```

`src/lib.rs`：

```rust,ignore
mod config;
mod error;
pub mod user;

pub use config::Config;
pub use error::Error;
pub use user::{User, UserService};
```

`src/user.rs`：

```rust,ignore
mod model;
mod repository;
mod service;

pub use model::User;
pub use service::UserService;

// repository 是实现细节，不需要公开。
```

`src/user/model.rs`：

```rust,ignore
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct User {
    id: u64,
    name: String,
}

impl User {
    pub fn new(id: u64, name: impl Into<String>) -> Self {
        Self {
            id,
            name: name.into(),
        }
    }

    pub fn id(&self) -> u64 {
        self.id
    }

    pub fn name(&self) -> &str {
        &self.name
    }
}
```

`src/user/service.rs`：

```rust,ignore
use super::{model::User, repository::UserRepository};

pub struct UserService {
    repository: UserRepository,
}

impl UserService {
    pub fn find(&self, id: u64) -> Option<User> {
        self.repository.find(id)
    }
}
```

这个布局体现了：

- `lib.rs` 只声明顶层模块和公共门面；
- 同一业务功能的模型、仓储和服务放在 `user` 目录中；
- `user.rs` 控制功能模块对外公开什么；
- 外部调用者不需要知道 `repository` 等内部路径；
- `main.rs` 使用 library crate，不重复定义业务模块。

## 9. 优先按功能组织，而不是只按技术层组织

小型项目常见的技术分层：

```text
src/
├── models/
├── services/
├── repositories/
└── controllers/
```

当项目变大时，同一个业务功能的代码会散落在多个远距离目录中。按功能组织通常更容易维护：

```text
src/
├── user/
│   ├── model.rs
│   ├── service.rs
│   └── repository.rs
├── order/
│   ├── model.rs
│   ├── service.rs
│   └── repository.rs
└── shared/
```

选择时可以遵循：

- 项目很小：保持扁平，不要提前创建大量目录；
- 业务功能逐渐独立：按功能建立模块边界；
- 多个功能真正共享且语义稳定：提取到明确命名的共享模块；
- 不要把暂时不知道放哪里的代码都扔进 `utils`、`common` 或 `helpers`。

一个模块最好拥有清晰的职责和业务名称，而不是只描述代码形式。

## 10. 依赖方向

良好的模块组织应让依赖方向容易理解。一个常见方向是：

```text
进程入口 / 接口适配层
          │
          ▼
       应用服务
          │
          ▼
        领域模型
          ▲
          │
数据库、网络等基础设施实现
```

领域模型通常不应依赖具体数据库客户端、Web 框架或命令行解析器。可以在领域或应用层定义所需 trait，让基础设施模块实现它们。

Rust 允许模块彼此通过路径引用，但能编译不代表架构依赖就是合理的。出现大量双向引用时，应考虑：

- 提取双方真正共享的概念；
- 将协调逻辑移到更高层模块；
- 用 trait 反转具体实现依赖；
- 合并实际上无法独立变化的模块。

不要为了消除所有引用而制造过度抽象；目标是让变化边界和依赖原因明确。

## 11. 多个二进制程序

额外二进制可以放在 `src/bin`：

```text
src/
├── lib.rs
├── main.rs
└── bin/
    ├── admin.rs
    └── migrate.rs
```

这些二进制都可以复用 library crate：

```rust,ignore
// src/bin/migrate.rs
use user_service::Config;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::from_env()?;
    run_migrations(config)?;
    Ok(())
}
```

不要在每个二进制中通过 `#[path = ...]` 或重复 `mod` 共享代码。共享实现应放入 `lib.rs` 所属的库中。

## 12. 测试如何组织

### 12.1 单元测试放在被测模块附近

```rust
pub fn add(left: i32, right: i32) -> i32 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn adds_two_numbers() {
        assert_eq!(add(20, 22), 42);
    }
}
```

单元测试是被测 crate 的一部分，可以测试模块的私有实现。`#[cfg(test)]` 保证测试模块只在测试构建中编译。

### 12.2 集成测试放在 `tests/`

```text
tests/
├── public_api.rs
├── user_workflow.rs
└── common/
    └── mod.rs
```

集成测试中的每个顶层 `.rs` 文件通常都是独立 crate，只能通过公共 API 使用库：

```rust,ignore
// tests/public_api.rs
use user_service::UserService;

#[test]
fn creates_a_service() {
    let service = UserService::default();
    assert!(service.is_ready());
}
```

多个集成测试共享的辅助代码可以放在 `tests/common/mod.rs`，避免它被 Cargo 当成一个独立测试目标。

### 12.3 文档测试和示例

- 公共 API 的简短用法放在 rustdoc 文档注释中；
- 完整、可运行的使用场景放在 `examples/`；
- 复杂测试夹具和端到端行为放在 `tests/`；
- 私有边界行为放在模块内的单元测试。

## 13. 什么时候拆成多个 crate 或 workspace

不要因为文件数量增加就立即拆 crate。模块已经能提供命名空间和可见性控制。

适合拆成独立 crate 的信号包括：

- 组件需要被多个 package 独立复用；
- 需要独立发布或采用不同版本；
- 希望通过 crate 边界强制隔离依赖；
- 编译特性、目标平台或依赖集合明显不同；
- 有插件、过程宏等必须使用特殊 crate 类型的组件。

Cargo workspace 可以管理多个相关 package：

```text
project/
├── Cargo.toml
├── crates/
│   ├── domain/
│   ├── application/
│   └── persistence/
└── apps/
    ├── server/
    └── cli/
```

拆分也会增加版本协调、依赖配置和编译单元管理成本。先用模块形成清晰边界，确认边界稳定且确有独立需求后再拆 crate，通常更稳妥。

## 14. Prelude 模块是否值得使用

一些库会提供 `prelude`，集中重导出最常用的类型和 trait：

```rust,ignore
pub mod prelude {
    pub use crate::{Error, User, UserService};
}
```

调用者可以写：

```rust,ignore
use user_service::prelude::*;
```

Prelude 适合拥有大量高频、配套 API 的库，但会隐藏名称来源。小型库通常直接从 crate 根重导出核心类型就足够。不要把所有公共项都塞入 prelude。

## 15. 模块文档

模块级文档使用 `//!`，项级文档使用 `///`：

```rust
//! 用户领域模型与服务。

/// 系统中的用户。
#[derive(Debug, PartialEq, Eq)]
pub struct User {
    /// 稳定的用户标识。
    pub id: u64,
}

assert_eq!(User { id: 1 }.id, 1);
```

公共模块和重导出应形成可浏览的文档结构。可以运行：

```bash
cargo doc --open
```

检查调用者看到的 API，而不仅是源码目录看起来是否整齐。

## 16. 常见错误与反模式

### 16.1 在多个 crate 根重复声明同一文件模块

同时在 `lib.rs` 和 `main.rs` 写 `mod user;` 会让源码分别编入两个 crate，产生看似相同、实际属于不同 crate 的类型。应让 `main.rs` 导入 library crate 的公共 API。

### 16.2 把 `use` 当成 `mod`

`mod` 建立模块树，`use` 缩短已有路径。使用某个兄弟模块时通常写 `use crate::sibling::Item`，不是再次写 `mod sibling;`。

### 16.3 过度公开

到处使用 `pub` 会让内部实现变成兼容性承诺。优先私有，crate 内共享使用 `pub(crate)`，真正需要调用者访问时才使用 `pub`。

### 16.4 `lib.rs` 只写 `pub mod everything`

这会把文件布局直接暴露为公共 API。更稳妥的方式是让内部模块保持私有或受限，再通过 `pub use` 提供经过设计的门面。

### 16.5 建立巨大的 `utils` 模块

`utils` 往往逐渐变成没有内聚性的杂物箱。优先根据职责命名，例如 `validation`、`encoding`、`retry` 或 `clock`。真正通用且稳定后，再考虑提取共享模块或 crate。

### 16.6 模块拆得过细

每个结构体一个文件会造成大量跳转和样板声明。紧密协作、共同变化且规模较小的代码可以留在同一模块，等职责边界清晰后再拆分。

### 16.7 路径层级过深

`crate::a::b::c::d::Type` 可能反映内部组织，但不一定适合作为公共 API。可以在功能模块或 crate 根重导出主要类型，给调用者稳定的短路径。

### 16.8 循环依赖式设计

模块之间互相知道过多实现细节，会使修改困难。将协调放到上层、抽取共享概念或通过 trait 建立单向依赖。

## 17. 推荐的落地步骤

为一个新项目组织模块时，可以按以下顺序进行：

1. 先在少量文件中完成功能，不要提前设计十几层目录；
2. 识别共同变化、职责明确的业务概念；
3. 用模块封装实现，并保持默认私有；
4. 在功能模块入口重导出真正需要的类型；
5. 在 `lib.rs` 建立小而稳定的公共门面；
6. 让 `main.rs` 只负责配置、依赖组装和进程生命周期；
7. 单元测试靠近实现，集成测试只使用公共 API；
8. 用 `cargo doc` 从调用者视角检查路径；
9. 当模块边界已经稳定且确有独立需求时，再拆成多个 crate。

## 18. 一个最小但完整的布局示例

项目结构：

```text
calculator/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── main.rs
│   ├── error.rs
│   └── operation.rs
└── tests/
    └── calculate.rs
```

`Cargo.toml`：

```toml
[package]
name = "calculator"
version = "0.1.0"
edition = "2021"
```

`src/error.rs`：

```rust,ignore
#[derive(Debug, PartialEq, Eq)]
pub enum Error {
    DivisionByZero,
}
```

`src/operation.rs`：

```rust,ignore
use crate::error::Error;

pub fn divide(left: i32, right: i32) -> Result<i32, Error> {
    if right == 0 {
        Err(Error::DivisionByZero)
    } else {
        Ok(left / right)
    }
}
```

`src/lib.rs`：

```rust,ignore
mod error;
mod operation;

pub use error::Error;
pub use operation::divide;
```

`src/main.rs`：

```rust,ignore
use calculator::divide;

fn main() {
    match divide(10, 2) {
        Ok(value) => println!("{value}"),
        Err(error) => eprintln!("{error:?}"),
    }
}
```

`tests/calculate.rs`：

```rust,ignore
use calculator::{divide, Error};

#[test]
fn rejects_zero_divisor() {
    assert_eq!(divide(10, 0), Err(Error::DivisionByZero));
}
```

这个例子中，内部文件布局是 `error` 和 `operation`，但公共 API 是扁平的 `calculator::{divide, Error}`。调用者不依赖内部模块结构，项目以后更容易重构。

## 总结

Rust 模块组织可以归纳为以下原则：

- `lib.rs` 是库入口和公共 API 地图，`main.rs` 是程序组装入口；
- `mod` 声明模块，`use` 缩短路径，`pub use` 设计对外门面；
- crate 内跨模块优先使用清晰的 `crate::`、`self::` 和 `super::` 路径；
- 默认保持私有，只公开调用者真正需要的能力；
- 公共 API 不必照搬内部文件布局；
- 小项目保持扁平，规模增长后优先按业务功能拆分；
- 让依赖方向稳定，避免模块互相了解过多实现细节；
- 主要逻辑放进 library crate，让二进制、测试和 examples 复用；
- 先用模块建立边界，确有发布、复用或依赖隔离需求时再拆 crate；
- 通过测试和 `cargo doc` 从调用者视角检验模块设计。

好的模块结构不会让所有路径都最短，而是让职责、所有权、依赖和公共边界一眼可见。
